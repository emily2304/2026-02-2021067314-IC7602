# Funcionamiento de Redes, NAT inverso y VPNs

## 1. Viaje completo de un paquete: ida y vuelta

En la clase anterior se explicó cómo un paquete sale desde una máquina local, salta de router en router (usando tablas de ruteo y operaciones AND con la máscara de subred) hasta llegar a un servidor destino (ejemplo: pedir el *home* del periódico CRHoy). Hoy se cierra el ciclo: **qué pasa cuando el paquete llega al servidor y cómo se construye la respuesta de vuelta.**

### 1.1 Desempaquetado en el servidor destino

Cuando el paquete llega al servidor correcto, este lo **desempaqueta capa por capa**, en orden inverso al que se armó:

```
Trama recibida
   └─ Se quita el encabezado MAC        → queda paquete de Capa de Red (IP)
       └─ Se quita el encabezado de Red  → queda segmento de Capa de Transporte (TCP/UDP)
           └─ Se quita el encabezado de Transporte → queda el mensaje de Capa de Aplicación (ej. HTTP)
```

Con el mensaje HTTP ya aislado, el servidor lo interpreta y genera una **respuesta**.

### 1.2 Cómo se re-empaqueta la respuesta (con intercambio de IP/puerto)

Al bajar la respuesta por las capas, un detalle clave: **los campos origen/destino se invierten** en cada capa.

| Capa | Contenido agregado | Direcciones |
|---|---|---|
| Aplicación | Headers + payload + trailer de la respuesta | — |
| Transporte | Header + trailer de transporte | IP/puerto que era **destino** ahora es **origen**, y viceversa |
| Red | Header + trailer de red | Mismo intercambio a nivel de IP |

> El header de Red **no** contiene puertos (eso vive en Transporte); solo contiene IPs.

### 1.3 El regreso: el servidor también rutea

El servidor que responde **también tiene su propia tabla de ruteo**. Repite exactamente el mismo procedimiento que hizo el cliente al salir:

1. Toma el IP destino.
2. Ejecuta el **AND** contra cada máscara de las rutas candidatas.
3. Escoge la ruta de salida.
4. Resuelve con **ARP** la MAC del siguiente salto (router/hop).
5. Envía el paquete.

Esto se repite salto tras salto por Internet — **importante:** *la ruta de vuelta no tiene por qué ser la misma que la ruta de ida.*

### 1.4 Diagrama general (ida y vuelta)

```
 LAPTOP (MAC 3)          ROUTER LOCAL (NAT)         INTERNET              SERVIDOR
 192.168.0.150:31122                                (varios routers)      DESTINO
       |                        |                         |                   |
       |--- paquete src=192.168.0.150:31122 ------------->|                   |
       |                        |                         |                   |
       |                (1) NAT: cambia puerto            |                   |
       |                origen a 31132 y guarda           |                   |
       |                fila en TABLA NAT                 |                   |
       |                        |                         |                   |
       |                        |--- src=IP_publico:31132 ----------------->  |
       |                        |     (salta router a router: AND +          |
       |                        |      máscara, ARP, siguiente hop)          |
       |                        |                         |                   |
       |                        |                         |   (2) desempaqueta
       |                        |                         |   hasta capa app,
       |                        |                         |   arma respuesta
       |                        |                         |                   |
       |                        |  <---------------- respuesta src=Servidor,  |
       |                        |     dst=IP_publico:31132  (ruta de vuelta   |
       |                        |     puede ser DISTINTA a la de ida)  <------|
       |                        |                         |                   |
       |                (3) revisa TABLA NAT:              |                   |
       |                31132 -> 192.168.0.150:31122       |                   |
       |                        |                         |                   |
       |  <-- entrega vía switch (circuito virtual a MAC 3)|                   |
       |                        |                         |                   |
```

### 1.5 NAT inverso — el corazón del "camino de vuelta"

Cuando el router de salida hizo el NAT original, **guardó una tabla** que asocia el puerto público que asignó (ej. `31132`) con el par real `(IP privado, puerto original)` = `(192.168.0.150, 31122)`.

Cuando llega la respuesta:

1. El router revisa el **IP destino** del paquete entrante → es su propio IP público.
2. Consulta la tabla NAT usando el **puerto destino** (`31132`).
3. Encuentra que corresponde a `192.168.0.150:31122`.
4. **Rompe la capa OSI "limpiamente"**: modifica el IP destino (capa de Red) **y** el puerto destino (capa de Transporte) del mismo paquete.
5. Vuelve a correr la tabla de ruteo → detecta que es tráfico local → resuelve la MAC (MAC 3) → el switch arma el circuito virtual → entrega el paquete.

**Resumen del ciclo NAT:**

```
Salida:  IP privado:puerto original  →  IP público:puerto NAT   (se guarda en tabla)
Entrada: IP público:puerto NAT      →  IP privado:puerto original (se consulta la tabla)
```

## 2. Redes como "un chorro de bytes" (idea para entender VPNs)

Antes de explicar el VPN, Nereo plantea una idea:

> **A la red no le importa qué protocolo, qué capa o qué contenido va dentro del paquete. Al final, todo es simplemente una secuencia (arreglo) de bytes de tamaño variable.**

Consecuencias de esta idea:

- Un chorro de bytes se puede guardar en cualquier estructura de datos (un arreglo en Java, Python, C, etc.).
- **Cualquier canal capaz de transportar bytes puede transportar un paquete de red**, sin importar su capa de origen:
  - Bytes escondidos en los *frames* de un video de TikTok.
  - Bytes escritos en una memoria USB.
  - Bytes enviados como archivo adjunto de WhatsApp.
  - Señales de humo o un bombillo encendiéndose y apagándose (en teoría — no es práctico por la latencia).
  - **Mensajes SMS** (ejemplo real que se desarrolla más abajo).

Esta idea es la que permite construir túneles y VPNs: **se toma un paquete completo (con todas sus capas) y se mete como *payload* dentro de otro paquete de un protocolo distinto.**

## 3. Arquitectura de sockets y la interfaz virtual (base técnica del VPN)

### 3.1 Comunicación "normal" (sin VPN)

```
+----------------------+     +----------+     +----------------+     +-----------------+     +----------------+     +----------------------+
| Aplicación           | --> |  Socket  | --> | File Descriptor| --> | Device Driver /  | --> | Tarjeta de red | --> | Medio físico         |
| (memoria de usuario) |crea | (a nivel |     |                |     | Library de la    |     | física (NIC)   |     | (cable, wireless,    |
| ej. Python, Chrome   |     |  del SO) |     |                |     | tarjeta de red   |     |                |     | fibra...)            |
+----------------------+     +----------+     +----------------+     +-----------------+     +----------------+     +----------------------+
```

- El **socket** es la abstracción que usa el programador (`send`, `receive`).
- A nivel de SO, la aplicación/socket está representada por un **file descriptor**.
- El **device driver** conecta ese file descriptor con la tarjeta física real.
- Al crear el socket se especifica la **network interface** a usar (ej. la tarjeta cableada o la wireless).

### 3.2 La interfaz virtual (VIF / TUN-TAP)

Una aplicación de VPN puede **registrar una interfaz de red virtual** ante el sistema operativo (en Linux/OpenVPN se conocen como **TUN** o **TAP**). Esta interfaz virtual:

- Tiene su propio "device driver" (virtual), que en vez de hablar con hardware, **redirige los datos hacia el file descriptor de la aplicación VPN** (en espacio de usuario).
- No tiene IP público propio (mientras el servicio no está activo se ve "desconectada").

```
 ESPACIO DE USUARIO                    ESPACIO DEL SISTEMA OPERATIVO              HARDWARE
 -------------------                   -----------------------------              --------

 +--------+   socket sobre    +-------------------+     +------------------+
 | Chrome | ----------------> | Device driver      |<--->| File Descriptor  |
 +--------+   interfaz        | VIRTUAL (TUN/TAP)  |     | de la app VPN    |
              virtual (TUN)   +-------------------+     +------------------+
                                                                  |
                                                                  v
                                                          +------------------+
                                                          | Aplicación VPN   |
                                                          | (espacio usuario)|
                                                          +------------------+
                                                                  |
                                                     abre su propio socket
                                                     hacia el servidor VPN
                                                                  v
                                                          +------------------+     +-----------------+
                                                          | Socket real      | --> | Device driver   | --> Tarjeta de red física --> Internet
                                                          |                  |     | de la NIC real  |
                                                          +------------------+     +-----------------+
```

**Flujo de datos:** Chrome pide un socket *a través de la interfaz virtual* → el driver virtual lo conecta con el file descriptor de la app VPN → la app VPN recibe esos bytes en espacio de usuario → la app VPN los reempaqueta y los envía por su **propio** socket, que sí sale por la interfaz real hacia el servidor VPN (en el ejemplo, Virginia).

### 3.3 La modificación clave: la tabla de ruteo

Al levantar la VPN se agrega una **nueva ruta por defecto**:

| Subred destino | Máscara | Interfaz | Prioridad |
|---|---|---|---|
| `0.0.0.0` | `0.0.0.0` | Interfaz Virtual (TUN) | **Más alta** que la ruta por defecto real |

Como esta ruta tiene mayor prioridad, **todo el tráfico nuevo** (ej. Chrome hacia Netflix) hace el AND contra las rutas candidatas y termina saliendo por la **interfaz virtual**, no por la física.

## 4. Encapsulamiento del VPN — el paquete "dentro" de otro paquete

Cuando el paquete de Chrome (capas Aplicación/Transporte/Red ya armadas) llega a la interfaz virtual, la aplicación VPN lo trata como **puro chorro de bytes** y lo mete completo como el *payload* de su **propia** capa de aplicación:

```
 PAQUETE FINAL QUE SALE A INTERNET (protocolo del VPN)
 ┌───────────────────────────────────────────────────────────────────┐
 │ Capa Física / Data Access del VPN                                 │
 │ ┌───────────────────────────────────────────────────────────────┐ │
 │ │ Capa de Red del VPN (header + trailer)                         │ │
 │ │ ┌───────────────────────────────────────────────────────────┐ │ │
 │ │ │ Capa de Transporte del VPN (header + trailer)               │ │ │
 │ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │
 │ │ │ │ Capa de Aplicación del VPN                             │ │ │ │
 │ │ │ │ ┌─────────────────────────────────────────────────┐   │ │ │ │
 │ │ │ │ │ PAYLOAD = paquete ORIGINAL completo de Chrome:   │   │ │ │ │
 │ │ │ │ │   - Capa de Red de Chrome                        │   │ │ │ │
 │ │ │ │ │   - Capa de Transporte de Chrome                 │   │ │ │ │
 │ │ │ │ │   - Capa de Aplicación de Chrome                 │   │ │ │ │
 │ │ │ │ └─────────────────────────────────────────────────┘   │ │ │ │
 │ │ │ └───────────────────────────────────────────────────────┘ │ │ │
 │ │ └───────────────────────────────────────────────────────────┘ │ │
 │ └───────────────────────────────────────────────────────────────┘ │
 └───────────────────────────────────────────────────────────────────┘
```

Es decir: **el paquete original de Chrome (con sus 3 capas) viaja anidado, completo, dentro del payload de aplicación del túnel VPN.** Este paquete "envoltura" viaja por Internet de forma normal (con su propio NAT, su propio ruteo) hasta el servidor VPN (Virginia).

### 4.1 Qué hace el servidor VPN al recibir

1. Recibe el paquete "envoltura" y lo desempaqueta hasta extraer el paquete original de capa de Red de Chrome.
2. El servidor VPN **tiene su propia tabla de ruteo** y envía ese paquete hacia Internet **desde sí mismo**.
3. Al hacer NAT, cambia el **IP origen por el IP del servidor de Virginia**.
4. Resultado: cuando Netflix (u otro servicio) analiza de dónde vino la petición, **ve la IP de Virginia**, no la de Costa Rica.

### 4.2 Diagrama resumen del efecto "cambio de ubicación"

```
 +--------------------+  paquete       +-------------------+  Internet   +----------------------+  desempaqueta   +----------+
 | LAN Costa Rica     | -------------> | Router / ISP       | ----------> | Servidor VPN         | ---------------> | Netflix  |
 | (interfaz virtual  |  encapsulado   | Costa Rica         |             | (Virginia)           |  y hace NAT con  |          |
 |  activa)           |  (protocolo    |                    |             |                      |  IP de Virginia  |          |
 +--------------------+  VPN)          +-------------------+             +----------------------+                  +----------+
                                                                                                         Netflix "ve" la petición
                                                                                                         como si viniera de EE.UU.
```

**Resumen en una frase:** un VPN funciona modificando la tabla de ruteo para forzar todo el tráfico por una interfaz virtual, que encapsula el paquete original completo dentro de otro protocolo y lo envía a un servidor remoto, el cual lo desempaqueta y lo reenvía a Internet con su propia identidad (IP).

## 5. Ejemplo extremo: "VPN" usando mensajes SMS

Para reforzar la idea de "todo es un chorro de bytes", se plantea un caso extremo:

- **Escenario:** Nereo no tiene datos móviles (no puede salir a Internet). Emily sí tiene datos, pero no puede compartir wifi/hotspot. Ambos pueden intercambiarse SMS (limitados a 140 bytes ASCII visible).
- **Idea:** usar los SMS como "medio físico" para tunelizar el tráfico de Nereo a través del teléfono de Emily.

```
 TELÉFONO DE NEREO (sin datos)              CANAL SMS               TELÉFONO DE EMILY (con datos)
 +---------------------------+        (140 bytes c/u, ASCII)        +----------------------------+
 | App VPN                   |   paquete ~1300 bytes fragmentado    | App VPN                    |
 | (crea interfaz virtual)   | ------------------------------------>| (recibe SMS en buffer,     |
 |                           |     en ~14 mensajes SMS               | reensambla el paquete)     |
 +---------------------------+                                       +----------------------------+
                                                                                    |
                                                                                    v
                                                                          +--------------------+
                                                                          | Internet           |
                                                                          | (con la identidad  |
                                                                          |  de Emily)          |
                                                                          +--------------------+
```

Proceso:
1. La app en el teléfono de Nereo intercepta el paquete de red (vía su propia interfaz virtual).
2. Lo **fragmenta** en varios SMS de 140 bytes.
3. Los envía uno tras otro al teléfono de Emily.
4. La app de Emily los va guardando en un **buffer** hasta reunir todos los fragmentos.
5. **Reensambla** el paquete original y lo saca a Internet usando la tabla de ruteo de Emily (con su propia identidad/IP).
6. La respuesta hace el camino inverso.

> Es solo un ejemplo conceptual, no un mecanismo real optimizado. La conclusión: se puede mover un paquete de **cualquier** capa por **cualquier** medio capaz de distinguir entre 0 y 1 — incluso imprimir tramas en papel, escanearlas y reconstruirlas — aunque en la práctica el *delay* haría que las conexiones sufran *timeouts*.

## 6. Introducción formal al curso: Internetworking

- El concepto de **Internetworking** surge de conectar múltiples **sistemas autónomos** (una LAN o conjunto de LANs) que originalmente no sabían de la existencia de otras redes (universidades, empresas aisladas).
- Estas redes se interconectan mediante **protocolos de intercambio de información**.
- Tecnologías/topologías históricas: Ethernet (la que sobrevivió), Token Ring y FDDI (obsoletas).
- Origen histórico: sistemas IBM y sistemas digitales aislados (LANs independientes).

### 6.1 Nota histórica — evolución de velocidades

- En 1998 (referencia: capítulo "The Killing Switch" de *The X-Files*) una conexión **T3** de ~44.736 Mbps era la conexión más rápida disponible, existía en apenas ~3 ubicaciones de EE. UU. y costaba **más de medio millón de dólares**.
- Hoy una conexión doméstica común ya supera esa velocidad (ejemplo mostrado en clase: 320 Mbps).
- En ~28 años la velocidad típica del hogar superó ampliamente la conexión "premium" de 1998 — referencia también a la **Ley de Moore** (el poder computacional se duplica aproximadamente cada 2 años).

## 7. Toda red se puede describir con 3 métricas

Cualquier "red" (incluso una persona moviendo un floppy disk) se puede caracterizar por:

| Métrica | Definición |
|---|---|
| **Ancho de banda** | Cantidad de datos que se pueden mover por unidad de tiempo (relacionado con el espectro/Hz disponible en el medio) |
| **Delay (latencia)** | Tiempo que tarda la información en propagarse de un punto a otro sobre el medio |
| **Tiempo total de transferencia** | Cuánto tarda en completarse el envío de TODA la información |

**Ejemplo clásico ("sneaker net"):** transferir 800 TB por una conexión de 10 MB/s tomaría días o semanas. En cambio, copiar esos 800 TB a un disco físico y **transportarlo en carro** puede ser mucho más rápido en tiempo total — aunque el "ancho de banda" del viaje en carro parezca absurdo de medir así.

> Concepto histórico: **Sneaker Net** — las primeras "redes" eran personas caminando con floppy disks de una computadora a otra.

## 8. Tipos de redes por alcance geográfico

| Tipo | Nombre completo | Alcance típico |
|---|---|---|
| **PAN** | Personal Area Network | ~10 metros (ej. Bluetooth) |
| **LAN** | Local Area Network | Casa, oficina, restaurante |
| **MAN** | Metropolitan Area Network | Nivel de ciudad |
| **WAN** | Wide Area Network | Backbones de Internet |

- **En la práctica** solo se distinguen dos términos de uso diario: **LAN** (todo lo interno) y **WAN** (todo lo externo, es decir, todo lo que requiere "saltar" fuera de mi red).
- **La clasificación depende de la perspectiva.** Ejemplo del edificio de apartamentos:
  - El dueño tiene su conexión con el ISP → para él, eso es su WAN; dentro de su propio perímetro es su LAN.
  - Si un inquilino (Alan) instala su propio *access point* con DHCP/DNS/router propios, para Alan **su router es la LAN** y la conexión que le llega del dueño **es su WAN**.
- A mayor tamaño de red (LAN → MAN → WAN), aumentan: costo de expansión, necesidad de soporte 24/7, redundancia y la importancia de un **SLA (Service Level Agreement)**. En una LAN doméstica, si se cae la conexión, no hay penalización formal; en un ISP nacional, el SLA es crítico.

## 9. Medios de transmisión

### 9.1 Medios guiados (cableados)

El cable tiene **armaduras** (recubrimientos) que:
- Actúan como aislante frente a interferencia electromagnética externa.
- Hacen que la señal se degrade más lentamente (mantiene el ancho de banda por más distancia).
- Son "guiados": la transmisión viaja con direccionalidad definida (aunque deja un pequeño "eco"/feedback hacia atrás, análogo a un grito que deja un eco).

| Medio | Características |
|---|---|
| **Cable coaxial** | Referencia histórica de Ethernet ("libre de errores" por diseño); mucha armadura → difícil de doblar/instalar; tarjetas más caras. Poco usado hoy en el hogar. |
| **Par trenzado (UTP / RJ45)** | El trenzado de los pares forma una especie de "antena simple" que repele interferencia electromagnética del ambiente. |
| — Categoría 5 | Hasta ~100 metros; sin filamento central. |
| — Categoría 6 | Incluye filamento central + recubrimiento extra → mayor ancho de banda y permite **Power over Ethernet (PoE)** sin interferencia. |
| **Fibra óptica** | Transporta pulsos de luz. Modos: **monomodo** (luz viaja en línea recta, más rápida) y **multimodo** (la luz rebota dentro de la fibra). |

**Nota práctica:** el ancho de banda real está limitado por el **eslabón más débil**: una tarjeta de red de 1 Gbps conectada con un cable categoría vieja sigue limitada por el cable (cuello de botella).

**Power over Ethernet (PoE):** permite transmitir datos y energía eléctrica por el mismo cable, eliminando la necesidad de tuberías/cableado eléctrico separado — simplificó mucho la construcción de edificios.

### 9.2 Medios no guiados (wireless)

Viajan en todas direcciones por el ambiente (no están "guiados" por un cable), lo que los hace más propensos a interferencia y pérdida de paquetes.

| Medio | Nota clave |
|---|---|
| **Wireless (Wi-Fi)** | Puede perder alrededor del **50%** de los paquetes enviados; no se nota por el ancho de banda alto disponible y por mecanismos de reenvío/segmentación (se verán más adelante). |
| **Satelital** | Generalmente requiere **línea de vista** entre antena y receptor para anchos de banda altos. |
| **Microondas** | También suele requerir línea de vista. |
| **Espectro electromagnético (general)** | Recurso regulado y "comercializable" — el gobierno cobra un canon por el uso de frecuencias (mención al conflicto sobre licitación de infraestructura 5G y empresas como Huawei). |

### 9.3 Comparación rápida guiado vs. no guiado

```
                              Medios de transmisión
                                       |
                 +---------------------------------------------+
                 |                                               |
          Guiados (cableados)                          No guiados (wireless)
                 |                                               |
     +-----------+-----------+                     +-------------+-------------+
     |           |           |                     |             |             |
  Coaxial   Par trenzado   Fibra óptica          Wi-Fi       Satelital     Microondas
            (Cat5/Cat6,   (monomodo /
             PoE)          multimodo)
```

## 10. Resumen

1. **NAT es reversible**: el router guarda una tabla puerto↔(IP,puerto) que le permite reescribir la respuesta y entregarla al equipo correcto dentro de la LAN.
2. **La ruta de ida no tiene que coincidir con la ruta de vuelta.**
3. **Toda la red, vista de forma abstracta, es solo un chorro de bytes** — esta idea es la base conceptual de cualquier técnica de tunelización (VPN, esteganografía, incluso el ejemplo de SMS).
4. **Un VPN funciona modificando la tabla de ruteo** para forzar el tráfico por una interfaz virtual (TUN/TAP), que encapsula el paquete original completo y lo envía a un servidor remoto.
5. El servidor VPN hace NAT con **su propia IP**, lo cual "esconde" la ubicación geográfica real del usuario.
6. Cualquier red se caracteriza por **ancho de banda, delay y tiempo total de transferencia** — incluso el transporte físico de datos ("sneaker net") cuenta como red.
7. En la práctica solo se usan los términos **LAN** y **WAN**, y cuál es cuál **depende de la perspectiva** del observador.
8. Los medios guiados (cable) ofrecen mejor protección a la interferencia; los no guiados (wireless) son más prácticos pero pierden más paquetes (hasta ~50%).
